# Git vs SVN: Сравнение систем контроля версий

## 1. Почему в Git ветвление "дешёвое", а в SVN — "дорогое"?

**В Git:**
Ветка — это всего лишь **указатель** (ссылка) на определённый коммит. Создание ветки занимает доли секунды и практически не требует памяти, потому что Git не копирует файлы — он лишь создаёт новую метку в истории. Ветка в Git легковесная, поэтому их можно создавать и удалять без ограничений [[1]].

**В SVN:**
Ветка создаётся как **полная копия директории** на сервере. Это не манипуляция указателями, а реальное копирование файлов в отдельную директорию на сервере (/trunk, /branches, /tags). Это более медленная операция, требующая сетевого взаимодействия и занимающая место на диске. Поэтому в SVN веток обычно меньше, и они создаются только для крупных задач [[2]].

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

**Нет, нельзя.**

SVN — это **централизованная** система контроля версий. Вся история изменений хранится на одном центральном сервере. Локально у разработчика находится только рабочая копия файлов (без полной истории).

**Коммит в SVN** отправляется на центральный сервер сразу. Для этого требуется сетевое соединение и права на запись. Без подключения к серверу можно только локально редактировать файлы, но зафиксировать изменения (commit) невозможно [[2]].

В отличие от Git, где у каждого разработчика есть **полная локальная копия репозитория** со всей историей. Коммит в Git сохраняется только в вашем локальном репозитории. Чтобы поделиться им, нужна отдельная операция push. Поэтому в Git можно полноценно работать офлайн: коммиты, создание веток, просмотр истории — всё это доступно без интернета [[1]].

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

1. **Корпоративные проекты со строгим контролем**
   В крупных компаниях, особенно в банковском секторе или геймдеве, часто требуется строгий контроль над каждым файлом. Модель SVN «один сервер — одна истина» с чётким поэкземплярным контролем доступа проще для администрирования и аудита. SVN позволяет легко настроить права доступа на чтение и запись для отдельных папок и файлов в репозитории (в Git это сложнее и менее гибко) [[1]].

2. **Проекты с большими бинарными файлами**
   SVN исторически лучше справлялся с хранением больших неделимых файлов (дизайн-макеты, 3D-модели, аудио, видео) без необходимости установки дополнительных расширений. SVN умеет эффективно хранить дельты некоторых бинарных форматов. Хотя Git с помощью LFS (Large File Storage) решает эту проблему, SVN может быть проще в настройке для таких задач [[2]].

3. **Простая и линейная история**
   Для проектов, где важна максимальная простота и не предполагается активное ветвление, SVN может быть проще для освоения «непрограммистами» (например, команды, работающие с документацией). История проекта неизменна и находится в одном месте, что может быть критично для строгого соблюдения compliance и аудита в некоторых корпоративных средах [[1]].

4. **Централизованная модель для новичков**
   Централизованная модель проще для понимания новичками, привыкшим к работе с общим файловым сервером. Есть один источник истины, и его история неизменна, что снижает когнитивную нагрузку при обучении [[2]].
